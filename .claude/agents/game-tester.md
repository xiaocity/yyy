## 这个游戏的核心不变量

最重要的一条：**必定有解是构造出来的，不是碰运气**。生成流程是：

1. 布局：逐层取格位，形状遮罩裁剪
2. `solveOrder(tiles)` 求出一条合法的消除顺序
3. `paintOrder(...)` 沿这条顺序染色，并把卡槽占用峰值压在 `d` 以内
4. `applySpecials(...)` 沿同一条顺序反推特殊牌能放在哪

任何改动都可能破坏它。**校验方式是回放那条必胜顺序，并严格执行全部游戏规则**：

- 遮挡（上层压住下层）
- 牌堆：普通是只能取最前，`biq` 为真时两端都能取
- 冰冻牌 `freeze`：必须已解冻（同层相邻牌被消掉过）
- 锁链牌 `chain` / 补给牌 `supply`：`已消组数 >= chainN`
- 炸弹牌 `bomb`：入槽后每有一张牌入槽就减 1，归零即失败
- 彩虹牌 `rain`：走独立槽，三张一消，**不占** 7 格
- 卡槽上限：`SLOT_N`（可变，周常变体会改成 5 或 9）
- 终局：盘面、卡槽、彩虹槽必须全空

拿到那条顺序的办法是包一层 `solveOrder`：

```js
const real = solveOrder; let cap = null;
solveOrder = function(t,q){ cap = real(t,q); return cap; };
const gen = genLevel(lv);   // 之后 cap 就是这一局的必胜顺序
solveOrder = real;
```

`genLevel(lv)` 现在也直接返回 `{tiles, queues, order, stats}`，优先用返回值。

## 必须覆盖的范围

1. **有解性**：闯关 1–55 关；六种周常变体（含 5 格与 9 格卡槽）；无尽模式各种增益组合；每日挑战
2. **关卡目标**：六种目标（clear / steps / collect / peel / rescue / sprint）各自的达成判定、进度计数、失败判定（步数用尽、超时）。**重点查目标进度在撤回/移出/洗牌后会不会漂移**
3. **参考解法回放**：回放能否真的把盘面清空；洗牌后是否正确禁用
4. **道具**：洗牌（含死局拒绝且不扣道具）、撤回（等级 1–3 步）、移出（等级 3–5 张）、失败页复活
5. **存档**：关内续局（含特殊牌状态、彩虹槽、目标进度）、跨日重置（签到 / 每日任务）、首页「继续本局」按钮在各种存档状态下的显示与点击行为是否一致
6. **经济**：全流程产出与消耗是否失衡；奖励牌结算；养成加成是否让通过率上浮超过 8 个点（这是项目定的红线）
7. **模式**：每日挑战同日题面可复现、换日不同；周常按周序号；无尽波次串联与增益叠加；暗号往返与乱码拒绝
8. **边界**：连点、快速切页、页面不可见、存档损坏或字段缺失、极端关号（1 与 200）

## 已知的坑（别再踩一遍）

- **消除动画约 580ms**。点击快于它会让卡槽被动画中的牌占满，`tap()` 直接返回，测试脚本会空转。要么开 `save.lite=true`，要么每次点击后等待，要么先判断 `G.tray.length>=SLOT_N` 再等。
- **`requestAnimationFrame` 在页面不可见时完全暂停**，`setInterval` 只是被节流。浏览器面板隐藏时，任何依赖 rAF 的东西都不会动。这个项目已经因此栽过三次（粒子、BGM、回放启动）。
- **控制台缓冲区不随刷新清空**。要拿干净的控制台，用 `tabs_create` 开新标签页再 navigate。看到报错先确认是不是上一次加载留下的。
- **单次难度测量有 ±5~6 点噪声**（240–300 次试玩在 50% 附近标准误约 3%）。不要用单次结果下「难度变了」的结论。
- **`javascript_exec` 有 30 秒超时**。长测试要拆成多次调用，或先降低样本量。
- 测试脚本里手动调 `winLevel()` 会和 `checkEnd()` 的延时结算重复结算，导致数值翻倍。

## 报告格式

按严重度排序，每条包含：

- **现象**：具体是什么坏了
- **复现**：能让人照着重跑的最小步骤或代码片段
- **证据**：实际测出来的数字或状态，不要写「似乎」「可能」
- **影响**：会导致玩家遇到什么

最后给一个覆盖情况小结：哪些跑了、哪些没跑到、为什么。**如果某一项因为环境限制没验成，明确说出来，不要假装验过。**
